# The tool catalog: tools of compiled apps, as data

In a web app a tool is a JS module that `validate.mjs` can import, so the agents, toolsets, permissions and
`ai-tools.json` entries that name a tool can be checked against it. In a compiled app (Rust, C#) a tool is code, with
its contract and handler together as everywhere else (`framework.md`, "Tools"), registered when the agent is built.
Nothing outside the app can load it.

The **tool catalog** closes that gap. It is a JSON file, generated by the app itself, that lists every tool and
toolset the app registers: the contract without the handler. The capability index names it, and `validate.mjs` reads
it instead of importing modules.

```json
// ai/index.json (a compiled app): no "tools" entries; the catalog stands in for them
{
  "format": "ai-enablement/1",
  "toolCatalog": "tools.catalog.json",
  "agents": ["agents/assistant.md"],
  "skills": ["skills/review-session"],
  "toolsets": ["toolsets/reading.json"],
  "toolsConfig": "ai-tools.json",
  "memory": "ai-memory.json",
  "permissions": { "deny": ["approve_*", "export_*"] }
}
```

```json
// ai/tools.catalog.json — GENERATED by the app's catalog test; never edit by hand
{
  "format": "ai-enablement/tools/1",
  "generator": "crates/app/tests/ai_catalog.rs",
  "tools": [
    {
      "name": "list_artifacts",
      "title": "List the session's documents",
      "description": "Documents of the open session: kind, state, revision.",
      "effect": "read",
      "toolset": "session",
      "pages": ["session/*"],
      "inputSchema": { "type": "object", "properties": {}, "additionalProperties": false },
      "annotations": { "readOnlyHint": true }
    }
  ],
  "toolsets": [
    { "name": "session", "title": "Session", "description": "The open session.", "tools": ["list_artifacts"] }
  ]
}
```

## Rules

- **Fields** follow the tool contract: `name`, `title`, `description`, `effect`, and exactly one input contract,
  `inputSchema` (JSON Schema) or `parameters` (the shorthand). Optional fields: `annotations`, `outputSchema`,
  `toolset`, `pages`, `enabled`, `timeoutMs`. A runtime writes `inputSchema`, its own conversion of whatever the tool
  declared, so the catalog shows what the model sees. `when` and the handler are code and are not in the catalog.
- **Toolsets**: `{ name, title, description, tools: [names] }`, the toolsets the code defines. JSON toolsets in
  `toolsets/*.json` still work and may name catalog tools.
- **Stable output**: tools and toolsets sorted by name, keys in the order shown, two-space indent, LF line endings,
  and a final newline. The same code always gives the same bytes, so a diff in review shows exactly what changed.
- **Generated, checked, committed**. The app has one test, written at install (stacks/<id>/STACK.md, "Tools"), that:
  1. builds the agent's tool registry the way the app does, with a stand-in host;
  2. exports the catalog;
  3. compares it with the committed file and **fails when they differ**;
  4. writes the file instead when `AI_CATALOG_UPDATE=1` is set.

  So the catalog can't go stale without a red test, and `validate.mjs` always checks against the truth.
- **Web apps don't use it**: their tool modules are the source. The JS runtime warns about any index key it doesn't
  use, `toolCatalog` included, so leave it out of a web app's index.
- **At run time** a native runtime does not need the catalog: tools come from code. In debug builds it may compare the
  two and warn about drift.

## What validate.mjs checks with it

The same checks as for JS modules:

- every tool's contract (name, description, a refusable JSON Schema, a known effect);
- duplicate names;
- toolsets that name missing tools;
- agents and skills (`allowed-tools`) that name missing tools or toolsets;
- `ai-tools.json` keys that are not tools;
- which tools start off.

On a compiled stack an index without `toolCatalog` gets a warning: references to tools can't be checked without it.
